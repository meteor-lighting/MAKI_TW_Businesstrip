# Supabase migration

The application now uses Supabase Auth, Postgres, Row Level Security, and an
Exchange Rate Edge Function. Google Apps Script is no longer used by the
frontend.

## 1. Local environment

Copy `.env.example` to `.env.local` and set:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

The URL is the project URL, not the `/rest/v1/` Data API URL. The client also
normalizes the latter form defensively.

## 2. Create the database

Run every file in `supabase/migrations/` in filename order in the Supabase SQL
Editor, or apply them with the Supabase CLI:

```sh
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

Deploy the exchange-rate function:

```sh
supabase functions deploy exchange-rate
```

## 3. Import the workbook

Run the read-only preflight first:

```sh
npm run supabase:import:check
```

For the live import, add the project's secret API key and legacy
`service_role` JWT to `.env.local`. Never prefix either value with `VITE_`;
that would expose it in the browser bundle. The secret key is used for database
rows, while the legacy key is used only for creating Supabase Auth users.

```dotenv
SUPABASE_SECRET_KEY=sb_secret_...
SUPABASE_SERVICE_ROLE_KEY=eyJ...
```

Find the legacy key under **Settings > API Keys > Legacy anon, service_role API
keys**. Keep it server-side and do not commit `.env.local`.

Then run:

```sh
npm run supabase:import
```

The importer is repeatable. It creates or updates Auth users, profiles, login
aliases, reports, expenses, cities, countries, and flight schedules. Existing
password hashes are never imported. Migrated users choose a new password from
the in-page reset form.

Employee IDs 16 and 17 share the same source email address. They are merged
into one Supabase Auth user, with both IDs and both names retained as login
aliases. Employee ID 17 is the primary profile because it owns the existing
report.

## 4. Supabase Auth settings

Under **Authentication > URL Configuration**, set:

- Site URL: `https://meteor-lighting.github.io/MAKI_TW_Businesstrip/`
- Production redirect: `https://meteor-lighting.github.io/MAKI_TW_Businesstrip/**`
- Local redirect: `http://localhost:5173/**`

The reset page is now opened from the sign-in screen. Users enter their existing
login and a new password twice; no email is sent.

The old reset URL generated by the application ended with:

```text
/?password-recovery=1
```

## 5. GitHub Pages

Replace the old `VITE_GAS_APP_URL` repository secret with:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_PUBLISHABLE_KEY`

The publishable key is safe in the browser because all private data access is
controlled by Postgres RLS. Never add the secret key to GitHub Pages.
